3.  Mathematical Proof — P2 Decode

MMON_SLAVE (Session 322/45335) was blocked on "library cache: mutex X" with the following parameters across all 62 ASH samples:

    P1 (idn)    = 1,950,821,498
    P2 (value)  = 13,237,089,206,272
    P3 (where)  = 124

In Oracle 11.2, the mutex holder's SID is encoded in the upper 32 bits of P2:

    TRUNC(13,237,089,206,272 / POWER(2,32)) = TRUNC(3082.06) = 3082

This is a mathematical proof that Session 3082 held the mutex. It is not an interpretation — it is arithmetic derived from Oracle's internal mutex encoding.

We have 62 consecutive ASH samples (08:47:12 through 09:23:03) showing this exact blocking relationship. Every single sample shows Session 322 waiting on "library cache: mutex X" with P2 decoding to SID 3082/44313 from drvl1078. There is no ambiguity.

Note: Between 08:53 and 09:16, the ASH in-memory ring buffer was overwhelmed by the sheer volume of waiting sessions (500+ concurrent sessions). Sampling resumed at 09:16, and Session 322 was STILL blocked by Session 3082 with the same P2 value — confirming the mutex was held continuously.

8.  Response to Previous Points

a) "No waiting event before 9:15 AM in EM top activity"

The AWR snapshot at 09:00 did NOT generate because MMON_SLAVE (Session 322) was blocked by Session 3082 — confirmed by 62 ASH samples showing MMON continuously waiting on "library cache: mutex X" from 08:47:12 to 09:23:03. ASH per-second data — which is stored independently of AWR snapshots — proves the storm began at 08:47:12.

b) "Listener problems since 08:50 — infrastructure issue"

Listener response degradation (20,840ms at 08:50:10) is a direct consequence of database-level mutex serialization. Every new database connection requires library cache access to parse the initial SQL. When Session 3082 holds the library cache mutex, connection establishment is blocked, causing listener timeouts. The listener itself had no independent problem — it resolved immediately when Session 3082 released the mutex at 09:23.

c) "sbpost2p Data Guard issues since 03:18 AM"

The standby database ORA-03113 at 03:18 is unrelated. Data Guard log shipping operates through LGWR/ARCH processes and redo transport, which do not cause library cache: mutex X contention on the primary. The 5-hour gap between the Data Guard issue (03:18) and the mutex storm (08:47) further confirms no causal relationship.

d) "CPU load increased after 9:15, not before"

During the storm (08:47-09:23), processes were not consuming CPU — they were WAITING on mutexes. "library cache: mutex X" is a Concurrency-class wait where sessions spin briefly then sleep. The load average of 2,628 confirms massive process pileup, but CPU utilization remains low because sessions are sleeping/waiting. When Session 3082 releases the mutex at 09:23, all 2,878+ queued sessions execute simultaneously — producing the CPU spike visible after 09:15. This is expected behavior after a mutex release.
