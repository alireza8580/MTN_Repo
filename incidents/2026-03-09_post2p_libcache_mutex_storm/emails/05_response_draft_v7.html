Conclusion

A single session from application server drvl1078 (SID 3082, schema ABL_DBOBJECTS, SQL*Plus) held a library cache mutex for 36 continuous minutes (08:47 to 09:23) while scanning archived redo logs. This blocked 2,878 sessions and generated 109,483 wait events across all application servers. When the session finally released the mutex, the storm ended immediately.

This session does not appear in any comparison AWR (March 7, March 8, 17 Esfand). It is the only difference between a normal day and the incident day. No DBA or infrastructure change was made on POST2P.

P2 mutex decode (mathematical proof)

MMON_SLAVE (Session 322/45335) was blocked on library cache: mutex X across all 62 ASH samples with these parameters:

P1 (idn) = 1,950,821,498 P2 (value) = 13,237,089,206,272 P3 (where) = 124

In Oracle 11.2, the holder SID is encoded in the upper 32 bits of P2:

TRUNC(13,237,089,206,272 / POWER(2,32)) = TRUNC(3082.06) = 3082

This is not an interpretation. It is arithmetic from Oracle's internal mutex encoding. 62 consecutive ASH samples, all with the same P2, all decoding to Session 3082/44313 from drvl1078.

Between 08:53 and 09:16, the ASH in-memory ring buffer was overwhelmed by 500+ concurrent waiting sessions. When sampling resumed at 09:16, Session 322 was still blocked by Session 3082 with the same P2 value, confirming the mutex was held continuously through that gap.

Regarding your previous points:

a) "No waiting event before 9:15 in EM top activity"
The AWR snapshot at 09:00 did not generate because MMON_SLAVE was blocked by Session 3082. This is confirmed by 62 ASH samples. EM top activity only shows aggregated snapshot intervals and cannot display data for a snapshot that was never created. ASH per-second data (stored independently of AWR) proves the storm started at 08:47:12.

b) "Listener problems since 08:50"
Listener degradation (20,840ms at 08:50:10) is a direct consequence of the mutex storm. Every new connection needs library cache access to parse SQL. When Session 3082 holds the mutex, connection establishment blocks, causing listener timeouts. The listener had no independent problem. It recovered the moment the mutex was released at 09:23.

c) "sbpost2p Data Guard issues since 03:18"
Data Guard log shipping uses LGWR/ARCH processes and redo transport. These do not cause library cache: mutex X on the primary. The 5-hour gap between 03:18 and 08:47 further confirms no relationship.

d) "CPU load increased after 9:15, not before"
During the storm, sessions were not consuming CPU. They were waiting on mutexes (Concurrency-class wait). The load average of 2,628 confirms massive process pileup, but CPU appears low because sessions are sleeping. When Session 3082 releases the mutex at 09:23, all 2,878+ queued sessions execute simultaneously, producing the CPU spike. This is expected behavior after a mutex release.
