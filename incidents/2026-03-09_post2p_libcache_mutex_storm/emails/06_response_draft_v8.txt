TECHNICAL REBUTTAL — Application Team's March 14 Post-Meeting Response

1. "SYS Session 322 = 68% blocking, application Session 3082 = only 8%"

This is misleading. Session 322 (SYS, MMON_SLAVE) is an Oracle background process that was BLOCKED BY Session 3082. The blocking relationship is proven mathematically:

    Session 322 waited on "library cache: mutex X" with P2 = 13,237,089,206,272
    TRUNC(13,237,089,206,272 / POWER(2,32)) = 3082

    This is Oracle's internal mutex encoding — the upper 32 bits of P2 contain the SID of the mutex holder.

The cascade chain is: Session 3082 (root holder) → blocks Session 322 (MMON_SLAVE) → Session 322's held mutexes cascade-block 2,878 sessions. The "68%" attributed to Session 322 is cascading impact from Session 3082. Citing 322 as the blocker while ignoring that 322 was itself blocked BY 3082 is like blaming a traffic jam on the second car in line while ignoring the accident ahead of it.

We have 62 consecutive ASH samples (08:47:12–09:23:03) confirming this chain without interruption.

2. "ORA-00600 errors — Oracle bugs"

The alert log entries cited:

    ORA-00600: [kkscxa_1]              at 08:52:43
    ORA-00600: [kgh_heap_sizes:ds]     at 08:52:43
    KGX cleanup, Mutex 3b1c0326a8(322, 0)

Key observations:
- The storm began at 08:47:12 (confirmed by ASH). These errors appeared at 08:52:43 — a full 5 minutes and 31 seconds later.
- The [kkscxa_1] error is "kernel kompile shared cursor add" — it occurs when the shared pool is under extreme contention, which is exactly what happens when a mutex is held for minutes instead of microseconds.
- The mutex reference "(322, 0)" in the KGX cleanup line refers to Session 322 (MMON_SLAVE) — the same session our analysis showed was blocked by 3082.
- These errors are SYMPTOMS of prolonged mutex holding, not independent bugs. They are expected consequences when a library cache mutex is not released for 36 minutes.

Presenting consequences as causes reverses the causality chain.

3. "No abnormal load observed"

We agree. The workload was normal. That is precisely the point — the same normal workload produced a 100,000x increase in mutex wait time. The only difference on March 9th was Session 3082's redo-scanning operation from drvl1078, which does not appear in any comparison AWR (March 7, March 8, 17 Esfand).
