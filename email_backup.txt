Dear Alireza,
Showing the proof of supporting them by NetBackup, does not necessarily mean that it’s feasible or better. Here I summarize several technical and operational concerns from the backup administration perspective.
While NetBackup documentation indicates support for these database platforms, implementing and operating database-native backups through NetBackup at our current environment, causes several challenges and risks that should be considered.

1. Configuration Complexity at Scale

Our environment contains a large number of database instances across multiple platforms. Implementing NetBackup-based backups for MySQL and PostgreSQL would require creating and maintaining extensive configurations, including:

Individual policies, schedules, and scripts Database credentials and connection configurations
Client-side agents and plug-ins Environment-specific tuning and testing
Managing and maintaining these configurations across hundreds of databases significantly increases administrative overhead and operational complexity compared to the current approach, where DBAs use native tools designed specifically for their platforms.

2. Increased Operational Risk

Database-native tools (such as mysqldump, pg_dump, or other platform-specific utilities) are tightly integrated with their respective database engines and are the most widely used and tested methods within the DBA community.

Introducing an additional layer through NetBackup creates dependencies between:

the database the NetBackup client/agent
backup policies external scripts
storage targets
Any issue within this chain could lead to failed backups or incomplete data protection.

3. Reliability and Restore Risk

Backup success alone does not guarantee recoverability. The most critical aspect of any backup strategy is reliable restore capability.

In many environments, database-native tools provide more predictable and well-documented restore procedures. NetBackup integrations sometimes rely on wrappers or connectors that may introduce edge cases or restore limitations, particularly during partial restores, point-in-time recovery scenarios, or version compatibility changes.

This adds an additional risk layer when fast and predictable database recovery is required.

4. Debugging and Troubleshooting Complexity

When using native database tools, troubleshooting backup failures typically involves a single layer: the database backup utility itself.

With NetBackup-managed database backups, troubleshooting may involve multiple layers:

Database utilities NetBackup agents
Policy configuration media servers
Storage targets (tape/Data Domain) network communication

This can significantly increase the time required to identify and resolve backup or restore issues.

5. Potential Software Bugs and Integration Issues

Although NetBackup provides support for multiple database platforms, integrations sometimes rely on specific plugin versions and compatibility matrices. In complex environments, this can lead to issues such as:

plugin compatibility problems after database upgrades unexpected failures due to agent bugs
limitations in supported database versions or features
These risks become more significant when applied across a large number of production databases.

6. Operational Stability

The current model separates responsibilities clearly:
DBAs manage database-native backups using tools designed for their platforms. The backup team manages enterprise backup infrastructure (NetBackup, tape, Data Domain).
This separation has provided a stable and predictable backup workflow for many years. Changing this model may introduce unnecessary operational dependencies between teams and systems.

ClickHouse is the only database on our list that does not have an official, dedicated NetBackup agent. To integrate ClickHouse into NetBackup, we will need to implement a workaround. The standard industry approaches are:
1.	Staging Backup (Recommended): Use ClickHouse's open-source clickhouse-backup utility to dump data to a staging area (like a local disk, NFS share, or S3 bucket), and then configure NetBackup to back up that specific staging directory.
2.	Snapshot Backup: Use LVM or file-system snapshots coupled with NetBackup pre/post scripts to momentarily freeze the ClickHouse tables while the snapshot is taken.
